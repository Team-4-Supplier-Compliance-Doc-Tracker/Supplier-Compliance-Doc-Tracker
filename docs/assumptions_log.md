| Do faker/pytest go in the Docker image? | No — only `src/` + stdlib in the runtime image; CI installs `requirements.txt` for tests | Image is replaceable and stays small; generator and pytest run on the host / in CI, not in production runs | Vedanshu | Agreed |
| How are DB backups made? | `scripts/backup.py` uses `Connection.backup()` + `PRAGMA integrity_check`; `scripts/restore.py` verifies the backup first, copies the live DB aside as `*.before-restore-<timestamp>`, then replaces; never prune (10 years). | How do we release / roll back? | Bump `__init__.py` + `pyproject.toml`, CHANGELOG, annotated git tag, pinned Docker tag; rollback = previous image tag on the same volume. | How are at-risk parts stored? | Own table `at_risk_parts` (check_id, part_number, supplier_id, reasons), one row per part per check; `flags` has no `part_number` | A flag is about a document or gap; at-risk is about a part and can have several reasons, so one `flags` row cannot hold it | Nikita | Agreed |
| What does `AtRiskPart.reasons` hold? | Strings `"<flag_type> <document_type>"` such as `"missing safety_cert"`, stored joined with `; ` and printed as is | Flag types alone ("missing", "missing") don't tell the manager which document is the problem | Nikita | Agreed |
| Who saves parts? | New `save_parts` in storage; the CLI saves documents and parts before running the rules | `at_risk_parts.part_number` is a foreign key to `parts`, and nothing else wrote parts | Nikita | Agreed |
| What happens when a document is re-sent with the same `document_id` but new dates? | The stored row keeps its old dates; the new ones are ignored because a duplicate `document_id` is skipped. A renewed certificate should arrive with a new `document_id`. The same applies to parts (a changed description is ignored). Flags and reports still use the new dates: rules run on the input file, and each flag stores its own expiry date | Follows from the skip-on-duplicate decision (2026-10-28); found in the PR #4 review | Nikita | Agreed |
| What happens when a renewal sits on file next to the document it replaces? | Expired and expiring soon judge only the current document per supplier and type: approved over pending, then the latest `issue_date`, then the later expiry. If the newest-issued document has already expired, the supplier is flagged even when an older one is still valid | Workflow research: SKU.io stores a renewal as a new document, so an old row would keep flagging a renewed supplier. Team decision in PR #14, not a customer answer (Q11) | Dheepthi | Agreed |
| How do we show a day with no issues (plan R13)? | With a clean subset (SUP-101 and PRT-5001), not by changing `--today` | Missing documents do not depend on the date, so `--today 2026-01-01` on the sample data still gives missing flags | Nikita | Agreed |
| What does `run` do when an input file is broken? | All three files are loaded and validated before the database is opened, so a missing or invalid file exits 1 with the file named on stderr and leaves no database behind | A failed run should not leave a half-written history or an empty database file | Nikita | Agreed |
| What does the report say about which day it covers? | `run` prints a first line `Compliance report as of <date> (tool <version>, check <id>)` above the report | `render_report` does not receive the date; the manager and an auditor need to know which day and which saved check the report is | Nikita | Agreed |
| How does the reader see suppliers that are fine? | `run` prints a second line: `Checked <n> suppliers and <n> parts: <n> suppliers with no issues, <n> parts at risk, <n> flags, <n> rejected records`. | What does `history` print for a supplier with no flags? | "no flags in any saved check" when the supplier is in the database, "no saved record of this supplier (rejected documents are not stored)" when it is not | Without this, a clean supplier and a mistyped ID look the same | Nikita | Agreed |

| Do the save functions keep the connection open? | No: `save_documents`, `save_parts`, `save_check` and the queries close the connection they are given, as DB-01 specifies; the CLI opens a fresh one per call | Follows the DB-01 ticket; avoids connections left open after a failure | Nikita | Agreed |
| How is the web UI built? | One server module and one HTML file, using only the Python standard library; no framework, build step or external scripts | Keeps the image dependency-free, and the demo works offline | Nikita | Agreed |
| Can the UI change or read arbitrary data? | No. It picks from fixed data sets and dates, never takes a file path, and cannot edit data, upload files or delete history | Reduces what can go wrong in a demo; history must never be pruned | Nikita | Agreed |
| How does sign-in work? | One account with a salted password hash and an in-memory session (8 hours, ended by a restart). The demo password is not in the repo. No roles and no HTTPS | Enough to protect a demo of synthetic data; a real rollout needs company sign-in and HTTPS | Nikita | Agreed |
